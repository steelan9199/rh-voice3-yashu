# 匹配响度标准（本技能唯一基准）

用户说「匹配响度」「对齐音量」「和上一个一样响」，一律按这份文件走，**不要自己另定目标值**。

## 标准素材

`assets/loudness-standard.mp3`（技能内置，14.4s / 48kHz / 单声道 / mp3 ~192k）

| 指标 | 立体声口径 | 单声道口径 |
|---|---|---|
| 积分响度 I | -14.4 LUFS | **-17.4 LUFS** |
| 响度范围 LRA | 4.2 LU | 4.2 LU |
| 真峰值 TP | -4.6 dBTP | -4.6 dBTP |
| 每声道 RMS | -17.0 dBFS | -17.0 dBFS |

表里的数字是对这个文件实测的，要复核就重测一遍。

## 目标值怎么取（唯一需要判断的地方）

| 素材声道数 | 目标 I |
|---|---|
| 单声道（BreezeTTS 产物都是） | **-17.4 LUFS** |
| 立体声 | **-14.4 LUFS** |

原因：EBU R128 对双声道求和。同一素材做成立体声，读数天然比单声道高 3.01 dB。
所以单声道拉到 -14.4 会**比标准响 3 dB**——这是最容易犯的错。

### 链式作业的坑：fx 会把单声道变成立体声

`fx` 产物固定 **48 kHz / 立体声**（空间感必须双声道才成立）。所以 `BreezeTTS 干声 → fx → lufs` 这条链上，`lufs` 会按**立体声口径**取 -14.4，把已经对齐好的 -17.4 又往上推 3 dB。

实测（2026-10-30 本机）：`assets/loudness-standard.mp3`（-17.4 LUFS 单声道）→ `fx --preset 电话听筒`（自动补 +3.80 dB，输出 -17.6 **立体声**）→ `lufs` 自动取 -14.4 → 推 +2.00 dB，被 TP 卡住停在 -15.9，报「还差 1.20 dB」。**看着像没调准，其实是目标选错了。**

两条处置：

- 链路最后一步是 `fx`：**不用再跑 `lufs`**。fx 默认已按输入响度线性补偿（要"远、轻"才用 `--no-level`）。
- 先 `fx` 又必须统一响度：**显式给 `--target -17.4`**，别让脚本按声道自动选。

## 用什么测（必须是这把尺子）

`ffmpeg -af ebur128`，不要用 `loudnorm` 的读数做基准。

实测两者差 **0.37 dB**：同一条素材 `ebur128` 读 -15.7，`loudnorm` 报 -16.07。
混用就会出现「按 loudnorm 调完，用 ebur128 一测还差 0.3 dB」的反复对不齐。

## 命令

```bash
cd ~/.workbuddy/skills/rh-voice3-yashu

# 单条
node scripts/rhv.mjs lufs "<音频>" 

# 批量（一次传多个）
node scripts/rhv.mjs lufs a.mp3 b.mp3 c.mp3

# 指定目标 / 换输出目录
node scripts/rhv.mjs lufs "<音频>" --target -16 --out ./norm
```

默认行为：按声道数自动选目标 → 量源文件 → 算线性增益 → 施加 → 复核 → 输出 `<原名>_std.<原扩展名>`，
**源文件不动**。mp3 统一重编到 192k，flac/wav 保持无损。

## 三条铁律

1. **只做线性增益，不做动态压缩。** 配音素材被压出泵动感就没法用了。LRA 处理前后必须一致（实测 4.2 LU → 4.2 LU）。
2. **真峰值只作约束，不作目标。** 默认 `--tp -0.5`，不要随手收紧到 -1.5。
   目标响度 -17.4 偏低，偏轻的素材要补不少增益：实测一条 -20.2 LUFS 的素材需 +2.8 dB，
   补完峰值正好到 -0.5——卡在 -1.5 就永远够不到目标。
   触顶时脚本宁可少给增益，并在输出里报「响度还差多少」，绝不上限幅器——限幅会改音色。
   `--json` 里对应 `cappedByTp: true`；看到它就别怀疑脚本坏了，是素材峰值已经贴顶（2026-10-30 实测：一条 TP=-1.5 的素材目标 -16，gain 给 0，输出停在 -19.6 并标 `cappedByTp`）。
3. **对齐口径而非对齐峰值。** 目标看积分响度 I，不是峰值。峰值只作为不越界的约束。

## 已知坑

- **mp3 头里的时长可能撒谎。** 碰到过文件头写 15.129s、解码却只有 14.42s 的素材（差 0.68s）。
  判断有没有被截断，要看解码后的实际长度（`ffmpeg -f null -` 末尾那行 `time=`），不能只信 `ffprobe format=duration`。
- **处理后必须复核。** 因为绝对门限（-70 LUFS）的存在，增益较大时积分响度不会严格按增益线性移动，
  所以脚本里加了「复核 → 残差 >0.15 dB 再补一次」的闭环。
